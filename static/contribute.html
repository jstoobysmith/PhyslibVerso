Contribute to the Physlib wiki

This wiki explains physics that has been checked, line by line, by a computer. The checking is done in a language called Lean — but the explaining is done in English, by physicists, and that is the part that is thin. If you know the physics, you are qualified to improve it today, without learning Lean and without installing anything.

1 Find a page Anything you know well. If you would rather be pointed at something, jump to where to start.
2 Press ✎ Edit Every block of prose on every page has one. Type into it like a document; there is a preview for your maths.
3 Press “Propose” It opens GitHub with your change already written up. A maintainer reviews it and credits you as a co-author.

What this wiki is (and what it is missing)

Physlib is a library of physics written in Lean, a language in which every definition is precise and every proof is checked mechanically. If a theorem is in Physlib, it is not “probably right” — it follows from its stated assumptions, and a computer has verified that it does.

What that guarantees is correctness, not comprehensibility. A formal statement says exactly what is true and nothing about why you would care, which convention was chosen, what the symbols mean physically, or which textbook chapter it corresponds to. That context lives in the prose between the code boxes — written by hand, in ordinary English, in what Lean calls docstrings. Many pages have a great deal of formalized physics and a single sentence of prose.

That gap is the contribution. A page with thirty proved lemmas and one line of explanation is not a finished page; it is a page waiting for a physicist. You are not being asked to check the mathematics — that is already done — but to say what it means.

Two libraries are shown here. Physlib is the reviewed one. PhyslibAlpha (marked with an orange α and a banner) is newer material that has not been reviewed to the same standard. Both are worth documenting; alpha pages often need it more.

What you can change without knowing any Lean

✅ Yours, right now

  • The page overview — what this file is about, and why.
  • The explanation of any definition or theorem: what it means physically, when it applies, what the assumptions really rule out.
  • Notation and conventions: signature, units, sign conventions, which of the two standard definitions is being used.
  • References: the textbook, paper or lecture notes this comes from.
  • Worked intuition: a limiting case, a picture in words, the standard example everyone is taught alongside it.
  • Typos, wrong words, broken English, stale statements.

🔧 Needs Lean (ask instead)

  • Changing what a theorem says, or its proof.
  • Adding a new definition or result, or a whole new page.
  • Renaming things, or moving them between files.

These are still worth raising — open an issue describing what is missing and someone who writes Lean can pick it up. Every page has an Ask a question button for exactly this.

You cannot break anything. Editing here never writes to the library. It composes a suggestion, which a maintainer reads and applies by hand. The worst possible outcome of a bad edit is that someone politely declines it.

Your first edit, step by step

  1. Open a page you know something about. Use the sidebar, the search box, or the roadmap. On a phone, the ☰ button top-left opens the page list.
  2. Find the prose. The paragraphs between the code boxes are the editable text. Each one carries a small ✎ Edit button — at the top-right of the block on a computer, and just underneath it on a phone.
  3. Press it. An editor opens on top of the page. It starts in Visual mode, which behaves like any text box: type, select, use the toolbar for bold, headings, lists, links and maths. If you prefer plain text, the Markdown tab shows the same content as source.
  4. Check your maths. The Preview tab renders the page exactly as it will appear, with $…$ typeset. Always look at it if you wrote a formula.
  5. Say why (one line). The “Why this change?” box is optional and disproportionately useful: it is the first thing a reviewer reads.
  6. Press “Propose on GitHub”. A new tab opens on GitHub with the title and the whole write-up already filled in, including a diff of your change. You press Submit new issue. That is the whole submission.

You need a free GitHub account to post the suggestion — signing up takes a minute and needs only an email address. Your draft is saved in your browser while you work, so you can create the account and come back to it.

What a good edit looks like

The bar is not literary. It is: would this have saved you five minutes when you first met this result? Concretely, the most valuable additions are the ones a formal statement structurally cannot carry — motivation, convention, scope, and provenance.

Before

# The damped harmonic oscillator

Basic definitions.

After

# The damped harmonic oscillator

A mass on a spring with a drag force proportional to velocity: $m\ddot x + b\dot x + kx = 0$. It is the simplest system in which energy is not conserved, and the standard model for any weakly dissipative oscillation — an RLC circuit, a pendulum in air, a damped mode of a field.

The behaviour is controlled by the ratio of $b$ to $2\sqrt{mk}$: under-damped (oscillates with decaying amplitude), critically damped, or over-damped. This file sets up the equation of motion and the damping ratio; the solutions are in Solution.

Convention: $b > 0$ throughout, and the damping ratio is $\zeta = b/(2\sqrt{mk})$ as in Goldstein §3.

Things that are always welcome

  • One sentence saying what the file is for, before any detail.
  • The physical reading of a symbol — “$\zeta$ is the damping ratio; $\zeta = 1$ is critical damping”.
  • The assumption that matters — which hypothesis is doing the work, and what breaks without it.
  • A pointer: “Goldstein §3.2”, “Peskin & Schroeder eq. (4.31)”, an arXiv number, a DOI.
  • The name people actually use for the result, if the Lean name is different.

Things to avoid

  • Restating the formal statement in words with nothing added.
  • Changing conventions or claims to match your preference — if the convention seems wrong, say so with the Report an error button instead.
  • Very long derivations. Link to the source; keep the page readable.
  • Editing the Lean code inside the code boxes. The editor does not touch them, and suggestions that try to are hard to apply.

Writing: maths, links and sources

The prose is Markdown with LaTeX maths. You do not have to memorise it — the toolbar inserts everything below — but here is the whole vocabulary you need:

You writeYou get
*emphasis*emphasis
**bold**bold
# HeadingThe page title (one per page, at the top)
## SectionA section heading
- itemA bulleted list
$E = mc^2$Inline maths, typeset with KaTeX
$$ … $$A displayed equation on its own line
`MassUnit`A Lean name — becomes a link to where it is defined
[text](https://…)A link

Maths. Anything between single dollars is rendered as LaTeX: $\hbar\omega$, $\partial_\mu F^{\mu\nu} = j^\nu$. Use $$…$$ for a centred display. The Preview tab is the fastest way to check a formula — a mistyped command shows up immediately.

Cross-references are free. Put a Lean name in backticks and the wiki turns it into a link to its definition automatically, on every page. So writing `MassUnit` in your paragraph connects it to the rest of the library at no cost to you.

Citing a source

There is no bibliography system; a plain sentence is the convention:

This follows Goldstein, *Classical Mechanics* (3rd ed.), §3.2.

See [Maldacena 1997](https://arxiv.org/abs/hep-th/9711200) for the original
statement, and Peskin & Schroeder eq. (4.31) for the conventions used here.

If you have a reference but do not want to write prose around it, the Suggest a reference button at the bottom of every page takes just the citation.

Reading a Lean page without knowing Lean

You can contribute without reading a single code box. But the code is readable at a glance once you know six things, and it helps to know what you are documenting.

What you seeWhat it means
def foo …A definition: it introduces an object or a piece of notation.
theorem, lemmaA statement that has been proved. Everything after := by is the machine-checked proof — you can skip it entirely.
:=“is defined to be”.
(x : ℝ)“x is a real number”. The colon gives the type of a symbol.
∀ x, P x“for every x, P(x)”. ∃ is “there exists”, → is “implies”.
{x : ℝ}The same, but Lean works the argument out for itself. Read it as ordinary quantification.

Every coloured name in a code box is live: hover it (or tap it) to see what it is and where it is defined. The Imports drawer at the top of the page lists what the file builds on.

The coloured cards

  • A blue Open problem card is a TODO left in the source: something nobody has done yet. Say what it would take, or point at the literature.
  • A green Informal definition or purple Informal lemma card is physics stated in words but not yet formalized. These especially need good prose — they are the bridge between the literature and the library.

What happens after you submit

  1. Your suggestion appears as an issue on the Physlib repository, containing your text and a diff against the current documentation.
  2. A maintainer reads it. If it needs discussion, they will reply in the issue — you will get an email.
  3. When it is accepted, the text is copied into the Lean source file and the commit credits you with a Co-authored-by: line, so the contribution is attributed to you in the repository history.
  4. The wiki rebuilds automatically, and your words are on the page.

Contributors who have opened the most documentation issues are listed on the front page.

Questions

Do I really not need to know Lean?

No. The editor works on the English prose only, and never shows you a proof. Knowing what theorem and := mean (see above) is enough to tell which paragraph goes with which result, and that is the whole prerequisite.

Do I need to install anything?

No. Everything happens in the browser — including on a phone. You never clone the repository, run Lean, or use git.

Why a GitHub issue rather than editing directly?

Because the text you are editing lives inside a Lean source file that must still compile. Routing through a review step means a contributor cannot accidentally break the build, and it keeps the barrier at “write a paragraph” rather than “learn git”.

If you are comfortable with GitHub, you are welcome to open a pull request against the source file directly — the View this page’s source file on GitHub link at the bottom of every page takes you there.

What if I am wrong, or I mis-remember a convention?

Then a maintainer says so and nothing happens. Suggestions are reviewed before anything changes; there is no way to damage the library from here. Being approximately right and specific is far more useful than being silent.

I lost my work / closed the tab.

Your draft is saved in your browser as you type. Reopen the same page and press Edit on the same block: it offers the draft back, and the Edit button carries an orange dot while an unsent draft exists.

My maths does not render.

Check it in the Preview tab. The usual causes are an unmatched $, a stray backslash, or a command KaTeX does not implement. Single dollars must hug the formula: $x$, not $ x $.

Can I add a whole new page?

New pages appear when new Lean files are added to Physlib, so that needs someone writing Lean. Open an issue describing the result you want covered and the source it comes from — a well-specified request is genuinely useful to the people who do formalize.

What is the α on some pages?

It marks PhyslibAlpha: correct in the sense that it compiles and is proved, but not reviewed to the same standard as the main library. Documentation there is just as welcome.

Going further

If the formalization itself starts to interest you, the natural next steps are the Physlib repository and the Lean community’s Zulip chat, where people are used to helping physicists get started. Mathlib’s site has the standard tutorials.

But that is optional. The wiki needs physicists writing English about physics far more than it needs another Lean user.
